# InkTrace V2.0-P2-06 Opening Agent 人本化重设计提案

版本：v2.0-proposal  
状态：已批准，作为 P2-06 v2.0 人本化设计依据  
日期：2026-07-10  
目标用户：只想写小说、不理解 AI 与软件工程术语的普通作者

> 本提案已经人工负责人批准，用于替代原 P2-06 候选设计中的产品流程与关键技术裁决。P2 架构、P2-06、P2-11 与 P2-12 已同步时，以同步后的正式文档为实现依据。

## 一、产品定义

### 1.1 用户看到的名字

产品内统一称为：**开篇助手**。

用户界面不得出现以下词语：

- Opening Agent
- Agent、Job、Session、Workflow
- ContextPack、CandidateDraft、HumanReviewGate
- Prompt、Token、模型角色、风险分数
- pending、blocked、failed 等内部状态

这些词只允许出现在开发者模式、设计文档和代码中。

### 1.2 一句话定位

开篇助手陪作者把一个小说想法整理成能吸引读者的前三章候选稿；它提供建议和草稿，但最终写什么、改什么、是否放进作品，始终由作者决定。

### 1.3 不是什么

- 不是自动替作者写书。
- 不是签约保证或流量保证。
- 不是模仿某本小说的工具。
- 不是必须先导入参考作品才能使用的功能。
- 不自动创建或覆盖正式章节。

## 二、核心设计原则

1. **先聊故事，不先填表。** 先问作者想写什么，再补必要信息。
2. **默认无参考作品。** 普通作者可以直接使用；参考作品只是可选增强。
3. **一次只做一个决定。** 每屏只有一个主要问题和一个主按钮。
4. **用作者语言。** 说“开头抓不抓人”，不说“钩子密度”；说“前三章要让读者期待什么”，不说“策略对象”。
5. **先给可编辑建议，再生成正文。** 作者能看懂、能改、能退回。
6. **不假装确定。** 不承诺签约，只说明“更符合常见网文开篇节奏”。
7. **随时退出，回来继续。** 已填写内容和已生成候选稿不丢失。
8. **AI 永远不替用户确认。** 生成、采用、应用、风险继续都必须由真实用户操作。

## 三、默认用户流程

用户只感知四步：

```text
说说你的故事
    ↓
选择开篇方向
    ↓
生成前三章候选稿
    ↓
逐章阅读与决定
```

系统内部可以有更多处理阶段，但不得把内部编排暴露给作者。

### 3.1 第一步：说说你的故事

入口文案：

> 想把故事开头写得更抓人？告诉我你准备写什么，我会先整理一份开篇思路，再由你决定是否生成前三章。

默认只问三个问题：

1. **这是一个什么故事？**
   - 自动带入作品题材和已有简介。
   - 作者可以用一两句话修改。
2. **主角现在最想要什么？**
   - 不要求填写完整人物卡。
3. **你希望读者看完第三章时最期待什么？**
   - 提供“想看主角反击”“想知道谜底”“期待感情发展”“自己填写”等白话选项。

如果作品已有大纲、人物和设定，系统自动读取，但只显示一句：

> 已参考你现有的大纲和人物设定。

不展示技术性的上下文列表。

辅助入口：**我还没有想清楚**。点击后使用选择题帮助作者梳理，不阻断主流程。

### 3.2 可选：添加灵感参考

第一步底部提供次要入口：

> 有喜欢的开篇节奏？可以添加一段作为灵感参考（可跳过）。

默认折叠，不主动要求用户导入。

添加前用白话确认：

> 请只添加你有权使用的内容。系统只分析开篇节奏和写法特点，不会把原文加入你的小说，也不会长期保存原文。

确认内容：

- `我确认有权将这些内容用于个人创作分析`
- 显示当前版权声明版本，但不向用户展示内部字段名。

输入限制：

- 最多 3 部参考作品。
- 每部最多前 3 章。
- 单部参考文本最多 30,000 个汉字。
- 超限时先让用户裁剪，不静默截断。

分析完成后，作者只看到：

- 开头进入冲突较快/较慢。
- 主角在第几段出现。
- 章节结尾通常如何留下期待。
- 哪些写法应避免过度相似。

不展示原文复刻片段，不提供“仿写某书”按钮。

### 3.3 第二步：选择开篇方向

系统生成 3 个差异明确的开篇方向，每个方向只展示：

- 一个易懂的名字，例如“先给危机”“先立人物”“先抛谜团”。
- 100 字以内的开篇说明。
- 前三章分别发生什么，每章一行。
- 优点。
- 可能的风险。

作者可以：

- `就选这个`
- `改一改`
- `换一批`
- `我自己写一个方向`

选择某个方向不是生成正文。界面必须明确：

> 这里只是在定开篇思路，还不会修改你的章节。

### 3.4 生成前的温和确认

只显示一张确认卡，不重复要求作者理解后台流程：

> 接下来会生成 3 章候选稿。它们会放在候选稿区，不会自动进入你的正文，你可以逐章修改、采用或丢弃。

如果没有参考作品，按钮为：`生成前三章候选稿`。

如果添加过参考作品，系统先做**策略级相似风险检查**：

- 低风险：正常生成。
- 需要注意：说明具体相似点，作者可修改方向或点击`调整后生成`。
- 高风险：不允许按当前方向生成，必须修改方向。

高风险提示不用恐吓式文案：

> 这个方向和参考作品的关键安排太接近。为了让作品保持原创，请先换一种开场方式。

### 3.5 第三步：生成前三章候选稿

生成过程中只显示作者关心的进度：

```text
正在准备第 1 章：让主角和核心问题尽快出现
第 1 章候选稿已完成
正在准备第 2 章：推进第一次冲突
……
```

不显示模型名、调用次数、内部步骤或日志。

生成规则：

- 一章一章生成并保存，前一章成功后再生成下一章。
- 每章独立成为 CandidateDraft。
- 某章失败时保留已完成章节。
- 用户可重试失败章节，也可停止。
- 停止后已生成候选稿全部保留。
- 不创建正式 Chapter，不覆盖已有章节。

结果允许 `partial_success`，但必须至少存在一个有效 `candidate_draft_id`。

### 3.6 第四步：逐章阅读与决定

生成后直接进入现有候选稿区，不另造一套审稿系统。

每章卡片展示：

- 本章想完成什么。
- 候选稿正文。
- “开头吸引力、人物出场、冲突推进、章尾期待”四项白话点评。
- 建议修改的 1–3 个重点。
- 若有参考作品，显示原创性检查结果。

作者可以：

- `应用到章节草稿`
- `修改后应用`
- `重新写这一章`
- `丢弃`
- `先放着`

每章独立决定，不提供“一键全部应用”。

应用仍走现有 HumanReviewGate 和 Local-First 草稿保存链路。

## 四、风险设计裁决

### 4.1 将风险检查拆成两次

现有候选设计把“生成前阻断”和“生成后警告”混为一谈。本提案明确拆分：

| 检查 | 时机 | 检查对象 | 高风险行为 |
|---|---|---|---|
| 策略相似风险 | 生成前 | 开篇方向、人物安排、场景顺序与参考分析摘要 | 阻止生成，要求调整方向 |
| 稿件原创性检查 | 每章生成后 | CandidateDraft 与结构化参考特征 | 保留候选稿，但禁止直接 apply，要求重写或用户明确处理 |

不得使用单一 `P2_IMITATION_RISK_HIGH` 同时表达两种风险。

建议错误码：

- `P2_OPENING_STRATEGY_SIMILARITY_BLOCKED`
- `P2_OPENING_DRAFT_ORIGINALITY_REVIEW_REQUIRED`

### 4.2 高风险不是前端提示，而是后端门控

高风险候选稿必须在 CandidateDraft metadata 中关联对应风险报告。现有 apply 用例读取该标记：

- 未处理 high risk：返回 blocked，不允许 apply。
- 重写后风险降低：允许进入正常 HumanReviewGate。
- P2 初期不提供“忽略高风险直接应用”，避免新增高风险 override 权限。

## 五、参考文本安全裁决

### 5.1 禁止写入通用 AIJob.context

完整参考文本不得写入普通 AIJob JSON context、业务表、AgentTrace、LLMCallLog、API response 或普通日志。

### 5.2 临时敏感存储

如实现必须跨请求保存参考文本，应使用独立 `TemporarySensitiveTextStore` Port：

- 本地加密存储。
- 每次导入生成不可猜测的 `reference_session_id`。
- 默认 TTL 30 分钟。
- 分析完成后立即删除，不保留到候选稿生成结束。
- 应用启动时清理过期残留。
- 成功、失败、取消均执行清理。
- 清理失败写安全审计，但不得写原文。

OpeningAnalysis 只持久化结构化特点、范围、标题、字数与不可逆 hash。

### 5.3 无参考路径是正式主路径

没有参考作品时，系统基于：

- 用户自己的题材、大纲、人物和设定。
- 内置的通用开篇检查规则。
- 用户选择的开篇目标。

不得把无参考路径推迟到 P2-S3；它是 P2-S2 的默认可用路径。

## 六、后台流程与状态机

### 6.1 采用分段用例，不维持一个长时间运行的 Job

普通作者可能隔几小时甚至几天才确认开篇方向，因此不让一个 AIJob 长时间等待用户。

分为四个短用例：

1. `prepare_opening_brief`
2. `generate_opening_directions`
3. `confirm_opening_direction`
4. `generate_opening_drafts`

每次模型处理可以创建短生命周期 AIJob；用户确认阶段由持久化业务状态承接，不靠运行中的 Job 等待。

### 6.2 用户可见状态与内部状态

| 业务状态 | 用户文案 | 可用动作 |
|---|---|---|
| `collecting_brief` | 还差一点故事信息 | 继续填写、退出 |
| `preparing_directions` | 正在整理开篇方向 | 取消 |
| `waiting_direction_choice` | 请选择一个开篇方向 | 选择、修改、换一批 |
| `checking_strategy_risk` | 正在检查原创性 | 取消 |
| `ready_to_generate` | 可以生成前三章了 | 生成、返回修改 |
| `generating_drafts` | 正在生成候选稿 | 停止 |
| `partially_ready` | 已完成部分章节 | 查看、重试、停止 |
| `waiting_draft_review` | 候选稿等你查看 | 逐章审阅 |
| `completed` | 开篇候选稿已准备好 | 查看候选稿 |
| `blocked` | 需要先处理一个问题 | 查看原因、返回修改 |
| `failed` | 这次没有生成成功 | 重试、返回 |

用户界面只显示中文文案，不显示内部枚举。

### 6.3 幂等与恢复

- 每个提交动作带 `idempotency_key`。
- 重复点击不得重复创建方向、Job 或 CandidateDraft。
- 每章生成使用独立幂等键。
- 应用重启后从业务状态恢复，而不是重跑已完成阶段。
- 重新生成方向保留旧方向为 `superseded`，不物理覆盖。

## 七、领域数据裁决

### 7.1 不覆盖历史记录

OpeningBrief、OpeningDirection、OpeningDraftBatch、OriginalityReport 均保留版本，不使用 `work_id UNIQUE + 更换主键覆盖旧记录`。

建议关系：

```text
Work
 └─ OpeningBrief v1..n
     └─ OpeningDirectionBatch
         ├─ Direction A/B/C
         └─ confirmed_direction_id
             └─ OpeningDraftBatch
                 ├─ CandidateDraft chapter 1
                 ├─ CandidateDraft chapter 2
                 ├─ CandidateDraft chapter 3
                 └─ OriginalityReport per draft/version
```

旧 CandidateDraft 永远可以找到当时使用的 Brief、Direction 和风险报告，不产生悬空引用。

### 7.2 单一权威状态

OpeningDirection 是方向确认的权威对象，不再同时使用 AISuggestion 状态和 OpeningStrategy 状态表达同一个确认门。

如需要在 AI 建议区展示，只建立只读投影视图，不形成第二套状态机。

### 7.3 一致性校验

后端必须校验：

- brief、direction、draft batch、work 属于同一作品。
- direction 必须是当前 batch 中可选且未过期的方向。
- 只有真实 `caller_type=user_action` 可以确认方向。
- 每个 CandidateDraft 的 chapter_no 只能为 1、2、3。
- 已存在正式章节时仍只创建 CandidateDraft。

## 八、API 设计方向

API 使用业务资源，不让前端拼装内部工作流：

```text
POST /api/v2/ai/opening/briefs
POST /api/v2/ai/opening/briefs/{brief_id}/references
POST /api/v2/ai/opening/briefs/{brief_id}/directions:generate
GET  /api/v2/ai/opening/direction-batches/{batch_id}
POST /api/v2/ai/opening/directions/{direction_id}:confirm
POST /api/v2/ai/opening/directions/{direction_id}:revise
POST /api/v2/ai/opening/directions/{direction_id}/drafts:generate
GET  /api/v2/ai/opening/draft-batches/{batch_id}
POST /api/v2/ai/opening/draft-batches/{batch_id}:stop
GET  /api/v2/ai/opening/works/{work_id}/latest
```

确认方向、停止生成等真实用户动作必须包含：

```json
{
  "caller_type": "user_action",
  "user_action": true,
  "user_id": "...",
  "idempotency_key": "..."
}
```

完整参考文本不得出现在任何 GET response。

## 九、白话文案规范

| 禁止文案 | 使用文案 |
|---|---|
| 初始化 Opening Workflow | 开始准备开篇 |
| ContextPack 不完整 | 现有故事信息有点少 |
| CandidateDraft 已生成 | 候选稿已经准备好 |
| strategy_not_confirmed | 请先选择一个开篇方向 |
| imitation risk high | 这个写法和参考作品太接近，需要换一种表达 |
| partial_success | 已完成部分章节 |
| blocked | 需要先处理一个问题 |
| Agent failed | 这次没有生成成功，可以重试 |

所有失败状态必须告诉作者：发生了什么、已经保留什么、下一步能做什么。

## 十、关键验收场景

1. 没有参考作品的新手作者能在三分钟内理解流程并开始生成。
2. 用户只填写最少三项故事信息，也能得到三个可理解的开篇方向。
3. 用户不理解任何 AI 技术术语，也能完成全部操作。
4. 未确认方向时不能生成候选稿。
5. AI、workflow、system 不能伪造方向确认。
6. 生成三章只产生 CandidateDraft，不创建或覆盖正式章节。
7. 第二章失败时第一章候选稿仍然保留，并可单独重试第二章。
8. 参考文本分析完成后完整原文被立即清除。
9. 进程异常退出后，过期参考文本能在下次启动时清理。
10. 策略级高相似风险阻止生成；稿件级高风险阻止 apply。
11. 每个旧候选稿都能追溯到当时的方向和原创性报告。
12. 普通界面不出现 Agent、Job、Session、Prompt、Token、caller_type 等术语。
13. 用户退出向导再回来，已填写信息和候选稿仍在。
14. 用户停止生成后，已完成候选稿全部保留。
15. 不提供“一键全部应用前三章”。

## 十一、明确不做

- 不承诺签约、流量或商业成绩。
- 不生成超过前三章。
- 不提供指定作品仿写。
- 不保存完整参考原文。
- 不自动应用候选稿。
- 不自动修改正式大纲、人物或设定。
- 不显示复杂评分仪表盘。
- 不让作者配置模型、Prompt 或 Agent。
- P2 初期不提供高风险稿件强制 override。
